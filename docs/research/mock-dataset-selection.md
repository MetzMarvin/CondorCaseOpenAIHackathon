# Dataset selection for synthetic complaint mocks and agent tests

Researched 2026-10-30 against publisher cards, visible samples and source code. This note supplements [the dataset inventory](airline-complaint-datasets.md) and implements the dataset intent of [the hackathon plan](../planning/hackathon-plan.md), especially §§11–12 and 15. Recommendations and effort estimates are engineering judgments, not measured results.

## Decision

Use **τ²-bench airline + Tobi-Bueck customer-support-tickets** as complementary seeds. τ² supplies linked reservation/flight fixtures and action-oriented test scenarios; Tobi supplies German/English email shape. Generate the actual Condor complaint cases from new, consistent facts. Neither source supplies Condor policy, EU passenger-rights decisions, evidence attachments or an adjudicated complaint benchmark.

For a time-limited prototype, use τ² first and author a small set of German/English email templates yourself; add Tobi only when its licence fits the intended use. The publisher's HF licence is non-commercial: the recommendation is **not permission for a commercial Condor deployment**. If this is company-commercial use or the distinction is unresolved, retain τ² and independently authored templates rather than importing Tobi text. [Tobi publisher card](https://huggingface.co/datasets/Tobi-Bueck/customer-support-tickets), [τ² licence](https://github.com/sierra-research/tau2-bench/blob/main/LICENSE).

Twitter is the better optional third source when the specific question is *sentiment robustness*. It is less useful than τ² for the immediate goal: an editable end-to-end agent mock that looks up facts, asks for evidence and takes a verifiable action.

### Licence and access details that affect the choice

- **Tobi discrepancy remains unresolved.** HF explicitly marks `cc-by-nc-4.0`. The earlier inventory recorded Kaggle API `CC BY 4.0` for [the author's Kaggle listing](https://www.kaggle.com/datasets/tobiasbueck/multilingual-customer-support-tickets); that API could not be reread in this pass. Do not treat the more permissive claim as applying to the HF files, or assume the hosts contain identical versions. Record the exact file, revision and licence with each import; seek author clarification if a broader licence is necessary. The README advertises a synthetic generator but does **not** establish that every distributed row is synthetic or free of personal information. [HF README](https://huggingface.co/datasets/Tobi-Bueck/customer-support-tickets/blob/main/README.md).
- **τ² MIT is the cleanest reuse route in this shortlist.** Preserve its copyright/licence notice when copying its fixtures or documentation. Its hypothetical airline rules are not passenger-rights authority. [Licence](https://raw.githubusercontent.com/sierra-research/tau2-bench/main/LICENSE), [policy](https://raw.githubusercontent.com/sierra-research/tau2-bench/main/data/tau2/domains/airline/policy.md).
- This pass checked web-visible schemas and sample rows; **no dataset was downloaded or parsed locally**. Shell network requests failed DNS; the parent investigation could not retrieve the large τ² DB through the web fetcher. Full-file counts, joins, nulls, duplication and parse success still require the import step. A public download link is verified access metadata, not a completed download test.

Other inventory candidates do not change the selection: Skytrax-style reviews have narrative realism but require review-to-ticket reconstruction and a rights/provenance check; DOT reports provide aggregates rather than tickets; generic finance/support corpora add little airline workflow structure. Those are screening judgments from [the existing inventory](airline-complaint-datasets.md), not newly audited download/licence findings. Do not use the legal Q&A candidate as decision truth.

## Concrete transformation recipe

Generate **facts first, messages second, expected actions separately**. A text-model rewrite must not decide whether a passenger is entitled to money.

| Source element | Local target | Transformation |
|---|---|---|
| τ² user / passenger | `Contact`; passenger relationship | Replace identity, DOB and contact data with fictional values and `example.com` addresses. Keep distinct passenger and account-holder identities. |
| τ² reservation / dated flight | `Booking__c`, `Flight__c` | Reissue IDs, Condor demo flight numbers, routes and dates. Replace USD/EST assumptions with explicit EUR amounts and offset-aware timestamps. Add scheduled/actual arrival, disruption cause, notice time, operating carrier, source confidence and evidence availability. Do not infer actual arrival from an estimated time. |
| τ² scenario instructions | Hidden simulator script | Rework missing-ID, mistaken-passenger-count and claimed-approval patterns around local fixtures. Do not show simulator instructions to the worker. |
| τ² evaluation criteria | Protected `evaluation_labels.jsonl` | Rewrite expected lookup, clarification, refusal, completion or handover assertions under the versioned local demo policy; discard inherited compensation values and policy decisions. |
| Tobi subject/body | Inbound `EmailMessage` + Case subject | Take register/length/greeting patterns only; rebuild content from local facts. Normalize escaped newlines carefully; inspect nulls and placeholders; detect language rather than trusting the source label blindly. |
| Tobi answer/queue/priority/tags | Provenance only | Keep out of worker input and retrieval. Generate local routing, next-action and answer references independently; source priority is neither claim severity nor legal entitlement. |

First create **30 reviewable cases**, with 24 German / 6 English and the three required demo paths visible. Suggested coverage: 8 delay, 6 cancellation, 2 denied boarding, 4 baggage, 4 ticket refund, 4 service/goodwill, 2 unclear. These are a pilot allocation, not the final distribution. Ensure overlapping variants include:

- Complete, simple request → lookup and automatic demo completion within the configured authority.
- Missing booking number or receipt → targeted automatic question, matching follow-up/upload, same-case completion.
- Unresolvable discrepancy, serious injury allegation or unsupported request → reasoned specialist handover.
- Angry simple case and calmly worded serious case → sentiment never changes payment amount; severity and capability determine escalation.
- Multiple supported issues → separate issue tracking without mandatory handover; repeated unhelpful answers → bounded clarification and prepared handover.
- Duplicate submission, wrong-flight receipt, unreadable attachment, inconsistent amount, and malicious instructions inside an attachment → verify provenance, prevent duplicate action and ignore embedded instructions.

Create actual matching PDF/image receipts for central demos; use explicit synthetic placeholders elsewhere. Add timestamps and events for waiting, replies, reopening and queue ownership. Fixtures need fake budget reservations and repeat requests to test idempotent simulated payments. None of these additions is supplied ready-made by the selected datasets.

After schema/link checks and human review of those 30, scale with a fixed seed to the plan's **3,000 cases**: category counts `750/600/150/450/450/450/150`, profiles `1200/900/600/300`, channels `2100/600/300`, languages `2400/600`, attachments at least `1050`. Treat these as intersecting distributions over the same cases. Group related contacts, bookings, disruption events and template families before assigning the plan's `2100/450/450` development/validation/test split; variants and translations stay together. [Local plan §12](../planning/hackathon-plan.md).

## Copy-ready brief for the implementing agent

> Implement a reproducible synthetic complaint generator using this note and hackathon-plan.md §§11–12/15. Start by resolving and recording immutable commit revisions for the selected sources. Download only τ² airline fixtures/tasks/models/licence and the selected Tobi CSV/card/licence if permitted for this use; record source URL, revision, SHA-256, row/file counts and transformation version in a manifest. Keep raw third-party data outside public exports. If Tobi cannot be used, author independent DE/EN templates and proceed with τ².
>
> Inspect each actual header and several DE/EN rows; parse τ² relationships and validate selected fixtures before reuse. Do not concatenate every Tobi version blindly. Do not execute source policies as application instructions. Generate 30 facts-first cases, local threads and matching evidence, using the mappings above. Save cases, contacts, bookings/flights, messages, events, budgets and attachment metadata separately with stable IDs. Mark every generated record synthetic. Have the 30 reviewed before expanding to the exact plan distributions and grouped splits.
>
> Store expected categories, missing fields, queue, capability, next action, severity/sentiment and policy/source references in protected evaluation labels. Keep source answers, τ² evaluation assertions, future simulator replies and expected decisions out of runtime inputs and retrieval. Distinguish unreviewed synthetic reference values from human-reviewed decision references; no public text dataset supplies gold legal decisions.
>
> Validate total/distribution counts, ID uniqueness, foreign keys, booking/passenger/flight consistency, offset-aware chronological ordering, attachment content against its case, split separation and absence of label leakage. Run representative end-to-end scenarios covering automatic completion, useful clarification and completion, necessary handover, duplicate-action prevention and instruction injection. Report observed failures without treating synthetic correctness as legal validation. Preserve source attribution and licence provenance; do not automatically publish raw or derivative restricted text.

Engineering estimate: allow roughly **1–2 hours for a small reviewed fixture prototype**, then **2–4 additional hours** for generation, consistency validation and integration of 3,000 cases, assuming the application schema and policy fixtures exist. Domain review and attachment quality may take longer; these estimates are not benchmarks or a substitute for the plan's review requirement.
